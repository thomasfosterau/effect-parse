## 0.5.0

### Minor Changes

- [#85](https://github.com/thomasfosterau/effect-parse/pull/85) [`7287ad5`](https://github.com/thomasfosterau/effect-parse/commit/7287ad556f688dbb71267c422869e77a4149f313) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `Parser.failAt(offset, error)`, a parser that fails with a user error reported at a chosen offset. A check that can only run once a construct has parsed (`tryMap`, `filterOrFail`) can only fail where the construct started; returned from a `flatMap` continuation, `failAt` points the error at the part at fault instead, such as a mismatched end tag. Interpreted and compiled parsers report the same position ([#73](https://github.com/thomasfosterau/effect-parse/issues/73)).

- [#85](https://github.com/thomasfosterau/effect-parse/pull/85) [`7287ad5`](https://github.com/thomasfosterau/effect-parse/commit/7287ad556f688dbb71267c422869e77a4149f313) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `Parser.withFastPath(grammar, fast)`, a supported way to put a hand-written scanner in front of a grammar. Compiled code calls `fast(state)` first; it returns the grammar's value with `state.pos` where the grammar would stop, or `Parser.Defer` to run the grammar from the same offset. Interpreted runs use the grammar alone, so every error, `Syntax` tree and trace is exactly the grammar's. `Parser.verifyFastPath(grammar, fast, inputs)` runs both at every offset of every input, complete and partial, and returns the places where they disagree ([#78](https://github.com/thomasfosterau/effect-parse/issues/78)).

- [#85](https://github.com/thomasfosterau/effect-parse/pull/85) [`7287ad5`](https://github.com/thomasfosterau/effect-parse/commit/7287ad556f688dbb71267c422869e77a4149f313) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `Parser.mapOrFail(p, f, orFailWith?)`, the allocation-free form of `tryMap` and `filterMap`: `f` returns `Input.Fail` to reject a value, and compiled code compares the result with the sentinel instead of allocating and unwrapping a `Result` or `Option` on every success. `orFailWith` builds the user error (the `ParseError`'s `cause`) only on failure; without it, the failure has no cause, as with `filterMap`. Where V8 does not inline the callback and remove the wrapper (a large grammar that exhausts its inlining budget), a check on every token runs about 1.3× faster than with `tryMap` ([#66](https://github.com/thomasfosterau/effect-parse/issues/66)).

- [#85](https://github.com/thomasfosterau/effect-parse/pull/85) [`7287ad5`](https://github.com/thomasfosterau/effect-parse/commit/7287ad556f688dbb71267c422869e77a4149f313) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `Parser.mapSpan(p, (a, start, end) => b)` and `Parser.seqWith(parsers, (a, b, ...) => c)`, the allocation-free spellings of `map(withSpan(p), ...)` and `map(seq(...), ...)`: compiled code passes the offsets, or one value per parser, straight to the callback instead of building a tuple and a span object on every success. V8 often removes those allocations itself when it inlines the callback; in a large grammar that exhausts its inlining budget, a lexer that records spans runs about 10% faster with `mapSpan` ([#64](https://github.com/thomasfosterau/effect-parse/issues/64)).

- [#85](https://github.com/thomasfosterau/effect-parse/pull/85) [`7287ad5`](https://github.com/thomasfosterau/effect-parse/commit/7287ad556f688dbb71267c422869e77a4149f313) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - The overloaded exports have named types: `Parser.ParseFn`, `ParseSyncFn`, `ParsePeekFn`, `ParsePartialFn`, `ParseRecoverableFn` and `DispatchFn`, `Input.FromSourceFn`, `Token.LiteralFn` and `TakeUntilFn`, `Ascii.CaselessFn` and `Syntax.ParseFn`, each holding the same call signatures as before, so calls infer the same types. `SyntaxNode.toJSON()` returns the new `Syntax.SyntaxNodeJson` (`{ kind, start, end }`) instead of `unknown` ([#77](https://github.com/thomasfosterau/effect-parse/issues/77)).

- [#85](https://github.com/thomasfosterau/effect-parse/pull/85) [`7287ad5`](https://github.com/thomasfosterau/effect-parse/commit/7287ad556f688dbb71267c422869e77a4149f313) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `Compiler.runner(p, options?)`, a prepared runner for drivers that run one compiled grammar many times on states they own, such as a lexer reading a token per run. It returns a function of the state that returns exactly what `Parser.run(p, state, options)` returns, with the compiled form looked up once (and again only when the input kind, or complete versus partial, changes) instead of on every run.
  
  The JIT's generated entry now checks the state's end and reports a call-stack overflow as the same `TooDeep` failure itself, so every runner calls it directly instead of through a separate guard and a closure. On the drivers benchmark's lexer (240 K tokens, one per run), `Parser.run` takes 13.7 ms instead of 14.5, and `Compiler.runner` 11.0 ms: about 46 ns per token against 60 before ([#65](https://github.com/thomasfosterau/effect-parse/issues/65)).

- [#85](https://github.com/thomasfosterau/effect-parse/pull/85) [`7287ad5`](https://github.com/thomasfosterau/effect-parse/commit/7287ad556f688dbb71267c422869e77a4149f313) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `Parser.combinator(parsers, build, name?)`, for writing combinators whose inner parsers compile. `build` makes the combinator's step from the parsers' steps, which `Parser.Steps<Ps>` types. Interpreted, it receives their own steps; compiled, their compiled steps. A combinator written with `Parser.make` is opaque to the compilers, so it and every parser it runs stay interpreted ([#83](https://github.com/thomasfosterau/effect-parse/issues/83)).

- [#85](https://github.com/thomasfosterau/effect-parse/pull/85) [`7287ad5`](https://github.com/thomasfosterau/effect-parse/commit/7287ad556f688dbb71267c422869e77a4149f313) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `Parser.quiet(p)`, which runs a parser without letting it add to the expectations of later errors. A whitespace or comment skipper that matches zero or more times stops by failing, and what it would have accepted (`" "`, `"(:"`, ...) used to be listed in every error raised after it; wrapped in `quiet`, errors expect only what can actually fail there. When the parser succeeds, its hints and furthest failure are forgotten; when it fails recoverably without consuming input, its failure expects nothing. Compiled parsers treat it as an identity ([#74](https://github.com/thomasfosterau/effect-parse/issues/74)).

- [#100](https://github.com/thomasfosterau/effect-parse/pull/100) [`0a0f3b0`](https://github.com/thomasfosterau/effect-parse/commit/0a0f3b051319f7e5dc42ebdec14316dca695d2bc) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - `Token.takeUntilAny(literals)`: takes input up to the first occurrence of any of several literals, the search a multi-pattern prefilter makes. On byte input `Compiler.wasm` now compiles it, and `Token.takeUntil`, natively with WebAssembly SIMD: Teddy (as in ripgrep), which tests the first three bytes of every literal at sixteen positions at once with nibble-table lookups and checks each candidate in full. Elsewhere successive searches over one input remember where each literal next occurs, so each is searched for once per occurrence. Results are unchanged.
  
  When each of the first three positions holds at most three distinct bytes across the literals (one literal, or the case variants of a few), the search compares with `i8x16.eq` instead of nibble tables, and a candidate is checked with the widest loads its literals fill.

- [#80](https://github.com/thomasfosterau/effect-parse/pull/80) [`60c1810`](https://github.com/thomasfosterau/effect-parse/commit/60c1810c7f45281460559601e107d86c27717df6) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `Compiler.wasm`, a third parser compiler. It scans the input in WebAssembly, with code generated from the grammar, and builds the value with a generated JavaScript function that reads what the scan recorded, so results and errors are those of the interpreter, as with the other compilers. On the JSON benchmarks it parses strings, UTF-8 and UTF-16 bytes faster than `Compiler.jit`. It copies input into WebAssembly memory with standard `ArrayBuffer` views and `TextEncoder`, so it runs the same everywhere. Array input, streaming builds, and environments without `WebAssembly` or `new Function` use the JIT.

## 0.2.0

### Minor Changes

- [#39](https://github.com/thomasfosterau/effect-parse/pull/39) [`bb8efed`](https://github.com/thomasfosterau/effect-parse/commit/bb8efed7a31c4ca413cb43ba2f51dc66f3cc10fd) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `Parser.run(parser, state)`, which runs a parser on an `Input.State` you own and returns its output or `Fail`, like `parser.step(state)` but using the parser's compiled form when it has one. A lexer that keeps one state and `reset`s it before each token now runs its token parser compiled without allocating a state, a `Result` or a slice per token: about 1.9 times as fast as calling `step` on a reused state, and 15% faster than `parsePartial` with an `offset`. On failure the parser runs again interpreted from the same position, so the state holds the interpreter's failure; partial states run the build that handles partial input. A driver that only needs to know that a parser failed (it tries another, or skips a character) can pass `{ diagnostics: false }` to skip that re-run, keeping just the failure's `mode`: about 2.3 times as fast on a scan where most runs fail.
  
  `ParserStream.parseMany` now runs a compiled parser compiled, with one state per buffer, instead of always interpreting it: about 2.8 times as fast on a stream of CSV-like rows.
